# Video to Sprite Animation

Run the workflow from one invocation while preserving the user’s selected source frames and tool choice. Never replace selected video frames with a processed master, reconstructed motion, or rejected artifact.

Read [failure prevention](references/failure-prevention.md) for background-method changes, GPT Image, FPS changes, source-frame claims, or repairs to a rejected sequence.

## Defaults

- Mode: `automatic` only after the sequential decision gates, source-preview approval, transparency-proof approval, canonical color-reference approval for GPT Image, and final batch approval.
- Frame construction is fixed to `one-to-one-source`. Every output must derive from its corresponding selected video frame. Do not offer a frame-construction choice, and never put synthesized motion in a question: it is not an alternative the user picks between, it is an exception they raise. State the mode; do not ask it.
- Background removal is fixed to `GPT Image` through the built-in image-generation/editing tool. Do not offer a background-removal method choice.
- Canvas: 512 × 512 unless specified otherwise; playback: 12 FPS unless source timing or the user specifies otherwise.
- Pivot: fixed anatomical bottom-center root; keep both boots on the shared ground line.
- Sequence type: `natural-loop`, `ping-pong-loop`, or `one-shot`. A one-shot plays once -- an attack, death, cast or hit reaction -- and is not judged on a loop seam.
- Produce separate transparent PNGs, an exact-FPS MP4, and a GIF that loops for a loop and plays once for a one-shot. Both are composited on black. The MP4 is encoded losslessly at 4:4:4, because a lossy preview rings around a sprite edge and the ringing reads as a contaminated matte. GIF delays are whole centiseconds and most frame rates are not, so the delays are distributed to keep the loop its true length: 48 frames at 24fps become forty 40ms frames and eight 50ms ones, exactly 2.000s. The GIF loops by itself in any viewer and is the one to hand someone; the MP4 is the exact-timing reference.
- Runs live inside the project the sprites are for, under `sprites/`, and the tree is created on first use rather than ahead of time. Videos are dropped in `sprites/input/`, and each run gets `sprites/runs/<run-name>/` holding `source/` (the video and its extracted native frames), `authority/` (manifests, frozen prompts, frame contract), `frames/` (per-frame attempt directories and accepted PNGs), `qa/` (correspondence sheets, onion sheets, previews) and `output/` (final PNGs, MP4, GIF, `delivery-report.json`). Every script takes explicit paths, so this is a convention they follow rather than one they enforce -- but a run that invents its own layout cannot be compared with another, and cannot be resumed from disk after a worker dies, which the retry budgets assume it can be. Write `sprites/.gitignore` holding `runs/` when creating the tree: one run is thousands of PNGs and several videos, and the project's repository is not where they belong. Never create any of this outside the project, and never inside the skill directory.
- No rembg, color-key/chroma-key, flood-fill, OpenCV keyer, custom mask, external image API, or silent fallback may produce a delivered alpha channel. A chroma test on the source remains permitted, and required, for deciding which pixels to measure on; see the invariant below.
- Never request, discover, read, or configure an API key. If the built-in GPT Image tool is unavailable, stop and report that the required tool is unavailable.
- Before any computer-use action that controls a browser or native app, ask for explicit approval for the specific proposed action and wait. Approval for image generation or batch execution does not approve computer use.
- Retry budgets are per frame and counted in three separate places: output-stage moderation blocks (default 6), failed geometry gates (default 6) and failed colour gates (default 6). They come from a measured 25% acceptance rate -- roughly 40% of requests are blocked at random and another 35% come back re-illustrated -- so a frame needs about four attempts. Budgets of 4 and 2 blocked a third of a batch. Geometry and colour are counted apart because they are unrelated faults with unrelated fixes, and an attempt that failed both charges both. A usage-limit error or a worker that dies spends neither; the run pauses and resumes from disk. These three numbers are settable once, at batch approval, and frozen for the run.
- The frozen short prompt is used on every attempt, not held back for retries. Measured over 167 real calls it does not change the moderation rate (41% against 42%) but it halves re-illustration (28% against 40%) and nearly doubles acceptance (31% against 18%).
- The validation scripts need numpy and Pillow. Create the skill's own environment once with `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt` and call them as `.venv/bin/python scripts/...`. Inside Codex, its bundled runtime Python at `~/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/bin/python3` already has both; a bare `python3` does not.

## Execution modes

- `solo`: one agent runs every step, including the image calls. This is the default.
- `co-work`: an orchestrating agent runs every gate, manifest, registration and validator, and delegates only the image call, one frame per worker process, through `scripts/run_frame_worker.py` and [worker brief](references/worker-brief.md). The worker never copies, validates, selects, retries or judges its own output; attempts are reconstructed from the host's event stream, so a worker killed mid-turn still produces an honest record.

Both modes use the built-in image tool with no credentials, so `imageExecutionInterface` stays `built-in-image-tool` and `credentialMode` stays `none`. Record the mode as `executionMode` in the authority manifest and delivery report.

## Sequential decision gate

Before the first source-processing command, ask exactly one unresolved question with 2–3 concrete choices and wait for the answer. Continue one question per turn; never send a combined checklist, multi-question form, or treat one blanket “approve” as approval for several decisions. The only work allowed before the first answer is reading this skill, resolving the source, and preparing the run directory.

An invocation that names no source video is not an error, and not a reason to ask for a path in prose or hand the user a template to fill in: it is simply the state before gate 0. Gate 0 asks which clip, listing the two or three most recent videos in the project's `sprites/input/` with each one's FPS, duration and resolution, and "another path" as the last choice -- scanning is what keeps this to concrete choices instead of a blank field. When that directory does not exist yet, this is the project's first run: say so in one line, ask the same question with "another path" as the only concrete choice, and create the tree once the source is known. Gate 0b confirms the run name, defaulted from the source filename, so it is a confirmation rather than something to compose. Gate 0c asks whether the user has clean reference artwork for this character -- a character sheet, the original sprite art, a turnaround -- because that is the one colour input no part of this workflow can derive, and asking for it late means asking after the palette has already been decided by whatever the video happened to contain. Take it or take "no artwork, use the video", copy anything supplied into the run's `authority/` on receipt so it cannot move or change underneath the run, and record its path and SHA-256 there and then. This gate collects the artwork; it does not approve a colour reference, which still needs the proof and the measured variation that only exist later. All three obey the one-question-per-turn rule like every other gate. This applies to every invocation shape equally -- a bare call, the word `start`, or a vague sentence -- because a keyword the user has to remember is a keyword they will eventually get wrong, and the fallback for getting it wrong must be the same first question rather than a wall of instructions.

Confirm these decisions separately before execution reaches work that depends on them: sequence type, playback FPS, and canvas/pivot policy. Two things are not choices and must never appear as options in a question: background removal is built-in GPT Image only, and frame construction is `one-to-one-source` only. State each one; asking invites an answer that no part of this workflow is built to honour. After source inspection, separately approve the selected loop preview. After the proof is rendered, separately approve transparency/outline quality. Separately select and approve a canonical color-reference frame and color-consistency strategy, from candidates that include whatever artwork gate 0c collected at the start. Finally, ask one batch-execution question summarizing the already approved settings. Record each answer and its scope; do not re-ask a choice the user explicitly answered.

Use a choice question even when recommending a default. Put the recommended option first and explain its consequence briefly. If a decision needs visual evidence, pause, create it, show it, then ask the single approval question.

Every option in that question carries its own evidence. An option the user cannot see is not a choice, it is a request for another round trip, and placing it beside a rendered one makes the rendered one win by default -- the user approves what they can look at. So render both candidates and ask which, or render one and ask a plain yes/no; never show one preview and offer a menu. This also bounds the work, since naming an option is what commits you to rendering it. When the top candidates sit within the measurement's own noise, say that plainly and do not recommend on the metric: the ranking cannot separate them, and only the user's eye can.

These gates are separate because an answer's scope is exactly the question it was asked about. Merging them back into one checklist is how a transparency approval becomes read as permission to run a batch. Frame processing order is not one of these gates: frames are independent and may run in any order, or concurrently.

## Workflow

1. **Run sequential preflight.** Resolve the source and the run directory before anything else: when the invocation names no video, ask gate 0 from a scan of the project's `sprites/input/`, then gate 0b for the run name, then create `sprites/runs/<run-name>/` with its five subdirectories, write `sprites/.gitignore` if the tree is new, and pass those paths to every script from here on. Then ask gate 0c for clean reference artwork and copy anything supplied into `authority/` with its SHA-256 recorded. Then ask one choice at a time and wait after each answer. Confirm sequence type, FPS, and canvas/pivot policy before source processing; state frame construction as `one-to-one-source` rather than asking it. Ask the sequence type as its own question -- natural loop, ping-pong loop, or one-shot -- because it changes how the range is found and how the result is judged, and a clip that was never meant to repeat cannot be rescued later by a looser seam limit. State that background removal uses built-in GPT Image; do not ask the user to choose a method. Never offer synthesized motion here or anywhere else. A generic “approve” cannot approve multiple decisions.
2. **Inspect the source.** Record native FPS, duration, resolution, and source usability. Render a representative contact sheet. Read [motion planning](references/motion-planning.md).
3. **Confirm selection settings sequentially.** Ask only the next unresolved choice. Confirm the source range/native frames and sequence construction separately from any other setting. Do not infer a final range from a broad search range.
4. **Find the range.** Extract and score candidates at native FPS with `scripts/find_loop_candidates.py`. For a loop, the default mode ranks natural and ping-pong windows by how well the seam closes. For a one-shot, pass `--mode one-shot`: it ranks onset and settle boundaries by the rise and fall of motion instead, because there is no seam to hide and the loop scorer would return the quietest window in the clip -- the part where nothing happens.
5. **Approve the source preview.** Render the top two candidates in full -- strip, seam sheet and looping preview for each -- show both, and ask which to approve, keeping "inspect a different window" as the last option. Stop until answered. Naming the runner-up in text while rendering only the leader is not a choice between two windows: the user can only see one of them, so the one they can see is the one they approve. If the runner-up is not worth a render, do not list it; ask a plain yes/no on the leader instead. Say when the two are within the scorer's noise, as a near-tie is exactly when the metric stops being able to choose and the eye has to. For a one-shot, show each candidate's first and last frame with the motion phases between them rather than the seam.
6. **Freeze the selected-frame map.** Decode the approved frames at native resolution. Run `scripts/build_source_frame_manifest.py`; it records the fixed built-in GPT Image policy. The manifest must list every output frame, native frame, timestamp, source filename, and source SHA-256.
7. **Process one transparency proof.** Show the full-resolution transparent proof on checkerboard, white, and black, plus 100%/4× fragile-region crops. Compare it with that exact mapped source frame. Ask one transparency/outline approval question and stop until answered.
   - Review the proof on black as well as on checkerboard. A contaminated or ragged edge is close to invisible against a mid-tone check pattern and obvious against black.
8. **Approve color authority.** Show 2–3 color-reference choices: user-supplied clean artwork first whenever gate 0c produced any, then the approved proof/source frame, then another selected native frame. The artwork was collected at the start precisely so it is sitting here rather than being asked for now -- do not re-ask for it, and do not quietly omit it from the choices because the video frames are closer to hand. What stays at this step is the part that needs evidence to be informed: the proof has to exist to be a candidate, and the source's own frame-to-frame colour variation has to be measured before the strategy question means anything. Ask the user to select one, then show the chosen reference full-resolution and ask a separate approval question. Record its path, SHA-256, `role: appearance-only`, and approval in `authority-manifest.json`. Ask a separate question to choose `reference-guided-gpt` or `reference-guided-gpt-with-deterministic-palette-normalization`, and state the source sequence's own frame-to-frame colour variation measured in step 7 so the choice is informed. Recommend normalization whenever the source is stable, because the tool's colour error differs every frame and no per-frame check can see the flicker that results. A transparency approval is not color approval.
9. **Approve batch execution.** Summarize the already approved mapping, FPS, canvas/pivot, fixed built-in GPT Image policy, transparency proof, canonical color reference, and color strategy, and state both retry budgets and the two frozen prompt files. Ask one question: execute the mapped batch with those budgets, or revise one setting. Do not begin batch generation before approval. Once that is answered, ask one further question and stop until answered: run the batch in Fast mode or standard. Fast mode is the priority service tier -- roughly 1.5x speed, and it spends the usage allowance faster, which is what ends a long run early. State both halves of that trade when you ask; standard is the default and never assume Fast. Freeze `prompt.txt` and `prompt-short.txt` at this point and record both SHA-256 values in the authority manifest.
10. **Build the contract.** Run `scripts/build_frame_contract.py`. Read [frame contract](references/frame-contract.md).
11. **Process every mapped frame one-to-one with built-in GPT Image.** Run `scripts/frame_jobs.py init`, then `run`. Each output's edit input is its own mapped native frame: there is no second lineage and no parent to repair from. Pass the approved colour reference to `frame_jobs.py init --color-reference` so it reaches the tool as a second, appearance-only image; a reference recorded in the manifest but never sent guides nothing. Read [GPT per-frame editing](references/gpt-per-frame-editing.md) and [prompt templates](references/prompt-templates.md). Frames are independent: execution order is free, and each output is bound to its manifest index, never to its position in a directory listing. Do not use one canonical master as the timeline source. Do not request an API key or switch to an external API. The model settings are pinned per run rather than inherited: `frame_jobs.py run` passes `--model` and `--reasoning-effort` to every worker and adds `--fast` when Fast mode was approved, and each `record.json` carries the `model`, `reasoningEffort` and `serviceTier` the attempt actually ran on. Without that a change to `~/.codex/config.toml` mid-run silently re-models the remaining frames and no record says which frames came from which.
12. **Register each attempt onto its own native frame as it lands.** Run `scripts/register_to_authority.py`. It undoes the sub-pixel offset the image tool introduces, measured on the part of the sprite that is solid in the output and character in the source. Translation only, measured against that frame's own mapped native frame: this is not per-frame recentering, and an offset past the cap, a per-quadrant spread that indicates scale or warp, or a silhouette far from the source's own is a rejection, not something to trim into shape. Nothing here decides transparency: the source silhouette selects which pixels to measure on, and the delivered alpha stays the tool's. If the approved color strategy includes palette normalization, run `scripts/normalize_palette.py` after per-frame editing and before validation. It matches each material's colour to the same material in the frame's own mapped native frame, leaving alpha and geometry bit-identical. Material regions come from the native frame, never from clustering the output, because a mis-clustered region would be recoloured. Then run `scripts/lock_source_interior.py`. The tool redraws every line on every frame, and the lines land differently each time: measured between neighbours, 2.29% of interior pixels swung over 40 luma levels and sat on the artwork's own lines, at 66 times the local gradient of the flat areas. That is shimmer on every outline, and no colour gate sees it because it is not colour. Where the source is unambiguously the character -- eroded, and with no green spill -- its pixels are used directly, so the error there is zero by construction. The alpha stays the tool's: it alone decides what is transparent, and this changes only the colour of pixels it already called opaque. Never silently introduce recoloring when the user selected reference guidance only.
13. **Validate every output against its mapped source and color authority.** Render the per-frame comparisons with `scripts/build_pose_correspondence.py`, inspect them, and re-run it with `--accept <reviewer>` only for what you actually looked at; it fills the bindings and leaves every judgement false until then. Interior colour and linework are compared with the native source as each frame lands: with no approved parent to restore RGB from, nothing else would notice a recoloured or re-inked frame. Then run `scripts/validate_and_diagnose.py`, `scripts/validate_temporal_sequence.py` with `--frame-manifest` so a missing frame is named instead of letting the frames either side become neighbours, `scripts/validate_source_correspondence.py`, and `scripts/validate_color_stability.py`. The last one is the only check that can see colour flicker: every other colour measure compares a frame with its own source and passes two neighbours that are 2 and 9 levels off, which is exactly what flicker is. Both of those validators compare the last frame with the first, which is a join in a loop and simply the two ends of the action in a one-shot -- so pass the temporal validator `--loop-type` when the contract does not already carry it, and pass the colour validator `--loop` only for a loop. Supply a complete pose-correspondence report comparing each output with its exact source frame. Each record must accept silhouette, topology, equipment geometry, eye state and negative spaces, and link its comparison artifact. Inspect per-material color stability against the approved canonical reference.
14. **Normalize geometry safely.** Use one shared scale and integer translation with `scripts/normalize_validate.py`. Per-frame recentering is off by default; never independently crop, enlarge, or recenter frames. Registration onto a frame's own authority (step 12) is a different operation and is not affected by this: it is measured against that frame's own mapped source, never against a neighbour or a batch-wide average.
15. **Run visual QA.** Render the artifacts with `scripts/build_qa_artifacts.py`, passing `--loop-type` so a one-shot preview plays once instead of stuttering back to its first frame, then look at them. It writes `visual-qa-report.json` with every reviewed flag false; set them only for what you actually inspected. Read [quality gates](references/quality-gates.md). Inspect source/output pairs, previous/current/next triplets, normal and slow playback, the generated alpha-onion sheet, full-batch topology and landmark continuity, checkerboard, white, black, and color-reference comparison views. Write `visual-qa-report.json` using the required schema; a prose claim is insufficient. The script decodes the preview back and compares it with the frame it claims to show; if that check fails the report cannot complete, because reviewing edge quality on a lossy preview reviews the encoder.
16. **Validate and package.** Create `delivery-report.json` with `selectedSourceFramesOneBased` exactly matching the source manifest. Pass `visual-qa-report.json` to `scripts/validate_delivery_package.py`; package only when it returns accepted.

## Synthesized motion exception

Warping a master, transferring centroid/landmark/flow motion, generating new poses, interpolation, frame holds, or replacing a failed frame is not one-to-one processing.

Never offer this. It is not a mode to choose between, not a recommendation, and not a rescue to propose when frames keep failing -- a frame that fails stays failed and visible, and the remedy is another attempt or an honest blocked frame, never a synthesized substitute. The only thing that opens this path is the user raising it themselves, unprompted and in their own words, about work they already understand is no longer their video's frames. An approval the workflow went fishing for is not an approval: presenting it as an option is how a user ends up agreeing to something they never wanted, because the option appearing in a question implies the workflow considers it reasonable here.

Once the user has raised it, build `motion-reference-manifest.json` with `scripts/build_motion_reference_manifest.py`, classify outputs truthfully, and never report them as the selected video frames. Read [regenerative animation](references/regenerative-animation.md).

## Required invariants

- The approved source-frame list is immutable. At native FPS, use every selected frame exactly once and in order.
- For a selected range such as 154–201, output 1 derives from 154, output 2 from 155, through output 48 from 201.
- Background removal uses built-in GPT Image only; rembg and chroma-key extraction are not permitted workflow branches.
- GPT Image one-to-one mode edits every selected source frame individually. It may change pixels, but it may not substitute pose, silhouette, timing, equipment angle, or another frame.
- There is one lineage: every output is edited from its own mapped native frame. An authority or contract claiming a parent frame is rejected.
- A chroma test on the source may be used to decide which pixels to *measure* -- registration masks, identity and silhouette gates. It must never write a delivered alpha channel. Built-in GPT Image decides transparency.
- GPT Image batch processing requires a separately user-approved canonical color reference with `role: appearance-only`. It guides palette and rendering only and never replaces the mapped native frame as pose authority.
- Transparency-proof approval and canonical color-reference approval are separate. Neither implies the other, and neither authorizes batch execution.
- No one-master warping, centroid transfer, motion reconstruction, interpolation, holding, skipping, duplication, or reordering is allowed unless the user raised synthesized motion themselves, unprompted. Frame construction is never a question and synthesized motion is never an offered option, so a "yes" to a choice the workflow put in front of the user does not count and never did.
- `source-frame-manifest.json` is mandatory for one-to-one processing. Each record includes `sourceFrameRequired: true` and the source SHA-256.
- Validation must compare every output to the exact mapped source. Smoothness, pivot, palette, bounds, or master consistency cannot prove source correspondence.
- Temporal acceptance must include local alpha-silhouette, visible-area, bounding-box-size, and centroid step/acceleration gates. A global motion average cannot waive a local redraw pop.
- A gate threshold is never raised and never offered for raising. The threshold is the definition of an acceptable frame, so moving it does not repair anything: it reclassifies the failure as a pass and the sequence ships broken, with the record saying it was accepted. This covers every limit in the contract -- seam, silhouette change, visible area, bounding-box size, centroid step and acceleration, registration offset, per-material colour delta -- and it holds no matter how many frames are stuck behind one.
- Retry budgets are a different quantity, more attempts at the same standard, but they are set once at batch approval and frozen for the run: never raised mid-run to rescue a stuck frame. The gates have documented blind spots -- a colour gate cannot see redrawn linework, a per-frame gate cannot see flicker -- so resampling one frame twenty times and taking the first pass selects for the attempt that happened to land in a blind spot, and an unbounded budget turns imperfect gates into defeated ones. A frame that exhausts its budget is reported blocked and visible, which is a fact the user can act on. "Raise the budget and try again" is not: nobody can say whether the next attempt would be better or merely luckier, so it asks the user to authorize something they have no way to judge.
- The loop seam is a gate for a loop and a false failure for a one-shot. Judge the seam only when the approved sequence type is a loop, and never widen the seam limit to let a one-shot through: that also stops the gate catching a loop that genuinely does not close.
- Final delivery requires a machine-readable accepted visual-QA report covering normal speed, slow speed, triplets, onion skin, exact-source motion comparison, source/output pairs, topology, and named landmark continuity.
- Changing FPS invalidates the timeline. Rebuild the mapping directly from native frames rather than reusing a prior lower-FPS output.
- Canvas, camera, shared scale, ground line, and numerical pivot remain fixed. Preserve the complete character and all equipment.
- Enclosed gaps under the chin, arms, hair, equipment, and other negative spaces stay transparent and cannot inherit neighboring colors.
- Failed frames remain visible until repaired or explicitly blocked; never silently substitute another frame.
- Temporal instability has three separate causes and each needs its own remedy: placement (registration), colour (per-material normalization), and redrawn linework (locking the interior to the source). A gate for one is blind to the others, and an average over the character is blind to all three.
- Colour is a sequence property, measured per material. An absolute per-frame limit cannot see flicker, and neither can an average over the whole character: materials drift in opposite directions and cancel. Temporal acceptance must include a per-material frame-to-frame colour gate calibrated from the source's own variation.
- A strategy the workflow records must be one the workflow performs. Offering a colour strategy with no script behind it, or approving a reference that is never sent to the tool, is worse than not offering it.
- A QA artifact must match the frames it claims to show. A preview that introduces its own artifacts is not evidence about the sprites.

## Deliverable summary

Open the report with two lines: the absolute output directory, and the path to the exact-FPS MP4 inside it. Those are the two things wanted first, every time; do not bury them in prose further down. Then report frame count, FPS/order, exact selected native-frame list, source range, background tool, one-to-one classification, correspondence status, pivot/root deviation, topology and fragile-region results, repairs, blocked frames, and final delivery-gate status.
